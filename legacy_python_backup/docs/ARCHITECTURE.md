# 架构与数据说明

## 运行结构

```text
Delta Chat 私聊
      │
      ▼
deltachat-rpc-server / Delta Chat Core
      │  NewMessage
      ▼
DeltaAdapter ── 私聊、加密状态、发送者身份检查
      │
      ▼
BotService ── 指令、权限、状态机、限流
      │
      ▼
SQLite ── 业务表、消息去重、持久化 outbox、审计
```

应用是单进程单体服务。每条入站消息以 `(account_id, message_id)` 去重；业务变更和响应写入同一个 SQLite 事务。响应先进入 `outbox`，成功交给 Delta Chat Core 后再清空正文并标记已发送。

## 核心数据

| 表 | 用途 |
|---|---|
| `users` | HMAC 身份摘要、Delta Core 本地联系人/聊天定位、系统管理员标志 |
| `networks` | 网络名称、状态、加入码带密钥摘要、AES-GCM 密文和尾号提示 |
| `memberships` | 每个网络独立的成员编号、昵称、介绍、隐私设置、角色和联系方式 |
| `contact_requests` | 联系申请、双方确认时的联系方式快照及状态 |
| `blocks` / `bans` | 成员屏蔽和管理员封禁 |
| `reports` | 举报及处理结果 |
| `pending_actions` | 10 分钟有效的二次确认操作 |
| `incoming_messages` | 入站消息幂等键，不保存正文 |
| `outbox` | 可恢复的待发送响应和双方交换消息 |
| `audit_log` | 管理员操作记录，不写入联系方式和加入码 |
| `account_recoveries` | 48 小时有效的换号恢复申请、审批状态和审批人 |

加入码拥有约 130 位随机强度。数据库保存 `HMAC-SHA256(secret, code)` 用于校验，并保存 AES-GCM 密文用于管理员在加密私聊中查看；密钥由服务器 Secret 派生。成员身份以规范化地址的 HMAC 摘要保存；发送消息仍需 Delta Chat Core 的本地联系人 ID 和聊天 ID。

## 权限

| 操作 | 普通成员 | 网络管理员 | 系统管理员 |
|---|---:|---:|---:|
| 管理自己的资料与申请 | 是 | 是 | 加入网络后是 |
| 管理当前网络成员、加入码和举报 | 否 | 是 | 是 |
| 查看其他网络 | 否 | 否 | 是 |
| 创建、停用、改名网络 | 否 | 否 | 是 |
| 任免网络管理员 | 否 | 否 | 是 |
| 审批账号恢复 | 否 | 仅自己管理的网络 | 全部网络 |
| 直接读取成员联系方式 | 否 | 否 | 否 |

网络管理员不能处理任何管理员账号。系统管理员地址只来自服务器环境配置，不能由聊天昵称或自报身份获得。

账号恢复采用“公开成员编号定位、管理员线下核实、机器人私聊审批”。审批后，原 `membership` 只更换所属 `user_id`，因此成员编号、资料、角色、屏蔽关系和已完成联系记录保持不变。机器人从已完成记录中去重取得对方当前联系人名片，只补发仍在同一网络且双方未屏蔽的成员。仅凭成员编号不能恢复账号。

## 联系申请状态

```text
申请人确认
   │
   ▼
pending_target ──拒绝──► rejected
   │  │
   │  ├─撤销──────────► withdrawn
   │  ├─7 天──────────► expired
   │  └─退出/屏蔽/封禁► invalid
   ▼
processing ── 双方 outbox 均发送成功 ──► completed
```

申请保存申请人确认时的地址和版本。接收方确认时保存其地址和版本。确认之前若地址版本变化，操作失败并要求重新执行。`processing` 中分别跟踪双方发送；一方发送失败时，另一方不重复发送，失败的一方可安全重试。进程若恰好在 Core 接收消息后、更新 outbox 前崩溃，恢复后可能重复发送同一段联系方式，因此消息中保留同一个申请编号。

## 已知边界

- 身份对应 Delta Chat 账号地址；被封禁者使用新账号仍可能重新加入。
- 地址发送给对方后无法撤回。
- 应用删除不能自动删除对方设备中的消息。
- Delta Chat Core 的账号目录和历史消息需要在备份、恢复与数据删除运维流程中另外管理。
