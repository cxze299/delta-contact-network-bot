# 自动身份归并与名片交付恢复

## 身份归并

只信任 Core 接入层获得的私聊、加密状态、联系人验证状态和公钥。Webxdc 请求不能提供可信身份依据。

- 同一标准化账号地址继续使用原用户记录。
- 已验证的相同 OpenPGP 主公钥指纹，在同一机器人 Core 账号内归并。指纹按 OpenPGP 包计算，并已与真实 Core 邀请指纹核对。
- 旧数据尚无指纹基准时，允许以**相同 Core 联系人及相同私聊**且当前已验证作为一次性基准；这是现有部署已授权的兼容策略。存在矛盾的历史指纹时不走此路径。
- 同网络保留较早成员编号，资料采用最近更新值；隐藏、暂停、退出、移除、封禁优先保留。屏蔽、举报、历史申请等引用随事务迁移。
- 合并会使旧的未完成交换失效。原分享地址与当前账号不一致时，用户需要在小程序点一次“使用当前账号”。
- 旧用户记录作为审计关联保留并标记 merged_into，不再作为在线成员。旧独立网页登录凭据失效，当前账号的授权和管理员密钥授权按同一身份保留。
- 启动和后续私聊／小程序同步均执行检查。正常重复检查不再次迁移。

## 名片防重复

所有原生名片路径都先提交 SQLite 交付声明，再调用 Core。每次交付生成随机、不含个人信息的标识，作为 vCard 文件名。它不会改变名片地址、昵称或公钥。

1. 发送前再次检查适用的授权、网络和加密状态。
2. 如果明确在发送 RPC 前失败，允许安全重试。
3. 一旦开始发送 RPC，超时、进程退出、数据库提交失败都不能把记录自动改回待发送。
4. 后台按交付标识查询对应聊天中 **SELF 发出的** Core 消息。找到后只补记 Core 消息编号和已提交状态，不再次发送。
5. 查不到或无法查询时保留待核查状态，而不是猜测未发送。小程序管理员的“审核”和网页后台的联系申请区域会显示它。
6. 管理员让双方检查名片后，可以“结束交换，不重发”。这会关闭不确定交付、终止该交换；如果双方确实没有收到，可自行发起新的交换。

这保证应用不会对一次不确定交付自动重复调用发送接口，不声称邮件网络已经送达对方设备。若 Core 本地消息已被外部删除，系统仍不会据此自动重发。

## 验证和部署

运行 `python -m pytest`。关键测试位于 `test_identity_reconciliation.py`、`test_delivery_recovery.py`，并包括小程序和网页管理员权限测试。

`Database.initialize()` 自动执行幂等的第 7 版迁移。部署前保存加密数据库备份和旧 Compose／镜像；只更新代码，不更换机器人 Core 账号目录。回滚涉及数据库恢复时应停服务并同时考虑 Core 消息状态，不能只回滚发送队列而忽略已发消息。
